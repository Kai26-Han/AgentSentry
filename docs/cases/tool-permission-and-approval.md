# 权限、审批与竞争条件

[中文](#) · [English](../en/cases/tool-permission-and-approval.md)

> 以下是已保存实验的安全事实，按问题重新整理，并非本次文档调整重新实测。实验日期、样本与规则版本用于限定结论；新安装需自行复现，不包含原作者的运行数据库。

## 要解决什么问题

有效身份不代表无限权限；“已批准”也不代表审批执行时权限仍有效。并发请求、吊销、超时和参数替换可能使副作用越过原来的授权边界。

## 控制如何生效

- 身份、租户、固定参数和资源授权逐项校验；临时令牌检查与次数扣减原子化。
- `call_id` 绑定原动作；换参数返回冲突，同一调用不重复执行。
- 审批固定原参数摘要，批准执行时重新核对权限、状态、有效期、来源及处置。
- Web 事实卡确认绑定管理员会话、租户、审批和原参数，不能由模型的“已批准”文字代替。
- 安全决定提交失败时不执行；执行后的结果提交失败保留 unknown，不自动重做。

## 观察事实

2026-09-30，`deep-validation-v1` 的身份／审批组在真实 PostgreSQL、Redis 和 HTTP 路径运行两轮，每轮 13 项：八个不同提案共用两次额度只写入两次；同一 `call_id` 八次并发只执行一次；参数替换、暂停、先吊销后批准和决定提交失败均没有越权副作用。

| 缺口与修复 | 修复前 | 修复后及其含义 |
| --- | --- | --- |
| 审批 ORM 状态未刷新 | 并发批准虽只写一次，另一个请求可能返回 500 | 行锁后刷新实体，返回成功或状态冲突，仍只写一次 |
| 吊销与批准缺少共同序列化 | 吊销已提交仍出现一笔合成写入 | 共用授权行锁。吊销先提交则拒绝；有效批准先取得执行资格时可能完成，后续吊销不能撤回已执行动作 |
| 复核期间权限到期 | 初次检查后延迟 2.2 秒，到执行时已过期仍写入 | 提交执行决定前再检查，两轮均拒绝、零写入 |

后两项分别使用 `revocation-race-v1`、`approval-expiry-v1`。不要把合法并发操作的顺序取舍写成“吊销能取消一切进行中执行”。[脱敏观察摘要](evidence/boundary-observations.json)保留前后事实。

## 自己如何复现

先设置[离线学习环境](../learning/README.md#前置条件与命令约定)：

```bash
.venv/bin/python -m pytest -q tests/test_service.py tests/test_approval_review.py tests/test_v2_tenants.py
```

按[身份章节](../learning/02-identity-capabilities.md)和[审批章节](../learning/04-approval-safety.md)生成自己的正常、拒绝及人工复核证据。在线竞争需要真实数据库，不能用 SQLite 单元测试代替并发现场结论。

## 剩余边界

租户隔离发生在应用和 PostgreSQL schema 层；共享数据库凭据或宿主被攻破不在这些断言内。审批事实卡不能证明人不会受骗，参数和状态仍须由网关核验。
